Autenticación por tokens con Sanctum

Por qué las sesiones no sirven aquí

En unidades anteriores autenticaste usuarios con sesiones y cookies: el servidor recordaba quién había iniciado sesión. Ese modelo choca con el principio stateless de REST y no encaja con clientes que no son navegadores. La solución estándar son los tokens: tras identificarse una vez, el cliente recibe una cadena secreta que adjunta en cada petición:

Authorization: Bearer 4|hT9pLmXw2cRfGq8vN3sKd...

Cada petición se autentica a sí misma. Laravel Sanctum, instalado ya con php artisan install:api, implementa este modelo guardando los tokens (con hash) en la tabla personal_access_tokens.

AdvertenciaErrores frecuentes

install:api puede fallar a medias, en silencio: si routes/api.php ya existe de antes (por ejemplo, porque ya lo creaste en la sección anterior), el comando se detiene con ERROR API routes file already exists antes de llegar a instalar Sanctum — y la tabla personal_access_tokens nunca se crea. El síntoma llega más tarde y no es obvio: cualquier petición autenticada falla con Table 'personal_access_tokens' doesn't exist. Compruébalo con docker compose exec web ls database/migrations | grep personal_access_tokens; si no aparece nada, repite install:api (ya no dará el error de rutas, porque ahora solo le falta la parte de Sanctum) o publica la migración a mano con php artisan vendor:publish --provider="Laravel\Sanctum\SanctumServiceProvider" --tag=sanctum-migrations seguido de php artisan migrate.

Además, el modelo User necesita una columna para distinguir administradores de lectores — no viene de fábrica, la añades tú:

docker compose exec web php artisan make:migration add_es_admin_to_users_table --table=users
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->boolean('es_admin')->default(false);
    });
}

Emitir tokens: la ruta de login

El modelo User debe incorporar el trait HasApiTokens (compruébalo; los proyectos nuevos ya lo traen tras instalar la API):

// app/Models/User.php
use Laravel\Sanctum\HasApiTokens;

class User extends Authenticatable
{
    use HasApiTokens, HasFactory, Notifiable;
    // ...
}
// routes/api.php
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Hash;
use App\Models\User;

Route::post('/login', function (Request $request) {
    $request->validate([
        'email'    => 'required|email',
        'password' => 'required',
    ]);

    $user = User::where('email', $request->email)->first();

    if (! $user || ! Hash::check($request->password, $user->password)) {
        return response()->json(
            ['message' => 'Credenciales incorrectas'], 401
        );
    }

    $token = $user->createToken(
        'cliente-api',
        $user->es_admin ? ['juegos:escribir'] : ['juegos:leer']
    );

    return response()->json([
        'token' => $token->plainTextToken,
    ]);
});

POST /api/login con credenciales correctas:

{
  "email": "admin@tienda.test",
  "password": "secreto123"
}
HTTP/1.1 200 OK
{ "token": "6|Xk2mPq9wLr5tYv8uZj3nHs7bAcDf..." }

Con credenciales incorrectas:

HTTP/1.1 401 Unauthorized
{ "message": "Credenciales incorrectas" }
NotaConcepto clave

plainTextToken solo existe en el momento de la creación: en la base de datos se guarda un hash, igual que las contraseñas. Si el cliente pierde el token, no se recupera: se emite otro.

El segundo argumento de createToken() son las abilities. Un punto que conviene dejar claro porque no es obvio: 'juegos:escribir' no es una palabra clave de Laravel — es una cadena de texto que te inventas tú, sin significado especial para el framework. tokenCan('juegos:escribir') simplemente comprueba si esa cadena exacta está en la lista que pasaste a createToken(); podrías haberla llamado 'puedo-crear-juegos' o 'xyz123' y funcionaría igual. La convención recurso:acción (juegos:leer, juegos:escribir, juegos:eliminar, desarrolladores:escribir…) es solo eso — una convención, para que la lista de abilities se mantenga legible según crece la API, no una regla que Laravel imponga.

NotaConcepto clave

Fíjate en un detalle que puede parecer contradictorio: el ejemplo emite juegos:leer para un usuario normal, pero index()/show() son públicos (lo verás en la sección siguiente) — ninguna ruta de lectura llama a tokenCan(), así que esa ability no la comprueba nadie ahora mismo. No es un error: se emite por coherencia (todo token refleja el rol completo de quien lo pidió, no solo lo que hoy está restringido) y por si en el futuro decides proteger también la lectura de algo — el token del usuario ya estaría preparado, sin tener que reemitirlo. Una ability sin ningún tokenCan() que la compruebe no es errónea, simplemente no está gateando nada todavía.

Proteger rutas

Lectura pública, escritura solo con token:

// routes/api.php
Route::apiResource('juegos', JuegoController::class)
    ->only(['index', 'show']);                 // lectura pública

Route::middleware('auth:sanctum')->group(function () {
    Route::apiResource('juegos', JuegoController::class)
        ->except(['index', 'show']);           // escritura con token

    Route::post('/logout', function (Request $request) {
        $request->user()->currentAccessToken()->delete();
        return response()->noContent();        // 204
    });
});

Y dentro de un método protegido, exige la ability concreta:

// JuegoController.php
public function store(StoreJuegoRequest $request)
{
    if (! $request->user()->tokenCan('juegos:escribir')) {
        abort(403, 'El token no permite escritura');
    }

    $juego = Juego::create($request->validated());
    return (new JuegoResource($juego))
        ->response()->setStatusCode(201);
}

Los cuatro escenarios del contrato de seguridad

Prueba POST /api/juegos en las cuatro situaciones posibles:

1. Sin cabecera Authorization:

HTTP/1.1 401 Unauthorized
{ "message": "Unauthenticated." }

2. Con un token inválido o revocado:

HTTP/1.1 401 Unauthorized
{ "message": "Unauthenticated." }

3. Con el token de un lector (ability juegos:leer):

HTTP/1.1 403 Forbidden
{ "message": "El token no permite escritura" }

4. Con el token de un administrador (ability juegos:escribir):

HTTP/1.1 201 Created
{
  "data": {
    "id": 23,
    "titulo": "Baldur's Gate 3",
    "precio": 59.99,
    "precio_iva": 72.59,
    "genero": "RPG"
  }
}
AdvertenciaErrores frecuentes
  • Confundir 401 con 403. 401: no sé quién eres (sin token o token inválido). 403: sé quién eres, pero no puedes hacer esto. Distinguirlos es parte del contrato.
  • Guardar el plainTextToken en el código fuente o subirlo a Git. Es una credencial: trátalo como una contraseña.
  • Olvidar Accept: application/json al probar rutas protegidas: en vez del 401 en JSON, Laravel intentará redirigir a una ruta login que no existe y verás un error confuso.

Actividades

EJ4 · Protección de la API con Sanctum

  1. Implementa /api/login con emisión de token y abilities diferenciadas (juegos:leer para usuarios normales, juegos:escribir para administradores; necesitarás un campo es_admin en la migración de usuarios) y /api/logout con revocación del token actual.

  2. Deja index() y show() públicos y protege store(), update() y destroy() con auth:sanctum. Exige juegos:escribir en store() y update(), pero añade una tercera ability, juegos:eliminar, exclusiva para destroy() — la sección no te ha enseñado a emitir un token con tres abilities distintas, solo con dos; decide tú cómo se la concedes al usuario administrador.

  3. Protege igual la escritura de Desarrollador (EJ3 punto 5): index()/show() públicos, store()/update()/destroy() tras auth:sanctum, exigiendo una cuarta ability, desarrolladores:escribir (una sola, sin separar eliminar aquí). Un token de administrador debe llevar las cuatro abilities a la vez.

  4. Verifica desde Postman los escenarios del contrato:

  • Petición sin token (401)
  • Token inválido (401)
  • Token de lector intentando crear un juego (403)
  • Token de administrador creando un juego correctamente (201)
  • Token con juegos:escribir pero sin juegos:eliminar intentando borrar un juego (403)
  • Token con juegos:eliminar borrando un juego correctamente (204)
  • Token de lector intentando crear un desarrollador (403)
  • Token de administrador creando un desarrollador correctamente (201)
