POO aplicada: servicios e inyección de dependencias

ImportanteNormativa · RA-CE

Este bloque trabaja CE5.g: aplicar los principios y patrones de diseño de la programación orientada a objetos.

La POO que vimos en la UD4 la aplicaremos en esta unidad. Laravel es un catálogo muy completo de patrones y vamos a usarlos para solucionar problemas reales.

El problema: el controlador que crece

Tu index() puede llegar a realizar diversas funciones. Valida, busca, ordena e imagina que hasta detecta duplicados:

// ANTES — un controlador que hace demasiado
public function index(Request $request)
{
    $q = $request->query('q', '');

    // búsqueda
    $contactos = Contacto::when($q !== '', fn ($query) =>
        $query->where('nombre', 'like', "%$q%"))
            ->orderBy('nombre')
            ->paginate(config('agenda.por_pagina'));

    // detección de teléfonos duplicados (¿esto qué hace aquí?)
    $duplicados = Contacto::select('tlf')
        ->groupBy('tlf')
        ->havingRaw('COUNT(*) > 1')
        ->pluck('tlf')
        ->all();

    return view('contactos.index', compact('contactos', 'q', 'duplicados'));
}

Funciona, pero incumple el principio de responsabilidad única (la S de SOLID): el controlador debería coordinar, no decidir. Cada regla de negocio nueva lo hincha más, y nada de esto se puede probar sin simular una petición HTTP entera.

La solución: clases de servicio

La lógica de negocio se extrae a una clase propia. Créala en app/Services/:

<?php // app/Services/AgendaService.php

namespace App\Services;

use App\Models\Contacto;
#use Illuminate\Support\Collection;
use Illuminate\Contracts\Pagination\LengthAwarePaginator;

class AgendaService
{
    /**
     * Busca contactos por nombre, ordenados alfabéticamente.
     */
    public function buscar(string $q): LengthAwarePaginator //Antes Collection
    {
        return Contacto::when($q !== '', fn ($query) =>
            $query->where('nombre', 'like', "%$q%"))
                ->orderBy('nombre')
                ->paginate(config('agenda.por_pagina'));
    }

    /**
     * Teléfonos que aparecen en más de un contacto.
     *
     * @return string[]
     */
    public function duplicados(): array
    {
        return Contacto::select('tlf')
            ->groupBy('tlf')
            ->havingRaw('COUNT(*) > 1')
            ->pluck('tlf')
            ->all();
    }
}

Inyección de dependencias: el controlador no hace new

El controlador declara que necesita un AgendaService (se pasa como parámetro) y Laravel se lo entrega:

// DESPUÉS — el controlador solo coordina
use App\Services\AgendaService;

public function index(Request $request, AgendaService $servicio)
{
    $q = $request->query('q', '');

    return view('contactos.index', [
        'contactos'  => $servicio->buscar($q),
        'q'          => $q,
        'duplicados' => $servicio->duplicados(),
    ]);
}

Fíjate en que nadie escribe new AgendaService(). Al ver AgendaService como parámetro en el método, el contenedor de servicios de Laravel crea la instancia y la “inyecta”. Eso se llama inyección de dependencias, y su ventaja es el desacoplamiento: el controlador no sabe (ni le importa) cómo se construye el servicio.

¿Qué ventaja supone esto? Cambiar la implementación sin tocar el controlador

Laravel ya te crea un service provider por defecto, app/Providers/AppServiceProvider.php. Es donde puedes decirle: “cuando alguien pida X, dale Y en su lugar”. Esta acción se realiza en el método register().

Supón que quieres una versión alternativa del servicio, por ejemplo, que ordene por fecha de alta created_at. Creas la clase (AgendaPorFechaService) y le dices a Laravel que la use en vez de la original:

// app/Providers/AppServiceProvider.php
use App\Services\AgendaService;
use App\Services\AgendaPorFechaService;

public function register(): void
{
    $this->app->bind(AgendaService::class, AgendaPorFechaService::class);
}

bind() dice: “cada vez que algo pida AgendaService, dale un AgendaPorFechaService”. Esto sucede sin modificar ni una línea de código. Ese es el punto fuerte del desacoplamiento, y la base de los dobles de prueba que verás en la siguiente sección Pruebas, documentación y proyecto integrador.

El código del servicio AgendaPorFechaService quedaría así:

<?php // app/Services/AgendaPorFechaService.php

namespace App\Services;

use App\Models\Contacto;
use Illuminate\Contracts\Pagination\LengthAwarePaginator;

class AgendaPorFechaService extends AgendaService
{
    /**
     * Busca contactos por nombre, ordenados por fecha de alta y paginados.
     */
    public function buscar(string $q): LengthAwarePaginator
    {
        return Contacto::when($q !== '', fn ($query) =>
            $query->where('nombre', 'like', "%$q%"))
                ->orderBy('created_at')   // en vez de orderBy('nombre')
                ->paginate(config('agenda.por_pagina'))
                ->appends(['q' => $q]);
    }
}

Utiliza php artisan tinker para ejecutar los siguientes comandos y comprueba la ordenación (y también la paginación):

Los patrones de la unidad, con nombre

Ya has utilizado los siguientes:

Patrón / principio Dónde lo has usado
MVC La arquitectura de toda la unidad
Responsabilidad única (SOLID·S) Controlador delgado + AgendaService
Inyección de dependencias El type-hint del método index()
Active Record Eloquent: Contacto::create(), $c->delete()
Front controller public/index.php recibe todas las peticiones
Singleton El contenedor y las conexiones compartidas que Laravel gestiona por dentro
AdvertenciaErrores frecuentes
  • Crear el servicio con new AgendaService() dentro del controlador: funciona, pero pierdes el desacoplamiento y la posibilidad de sustituirlo en pruebas.
  • Mover al servicio también la presentación (que devuelva HTML): un servicio devuelve datos; la vista es cosa del controlador y de Blade.
  • Un servicio-cajón (UtilsService) donde cae todo: la responsabilidad única también aplica a los servicios.

EJ5 · DisponibilidadService: la lógica de préstamos como servicio

Tu aplicación necesita reglas que ningún ejemplo de la teoría resuelve. Diséñalas como servicio inyectable.

NotaConcepto clave

Hasta ahora el catálogo de videojuegos vivía en un array reconstruido en cada petición: marcar un videojuego como no disponible no podía sobrevivir a la siguiente petición. Con el modelo Eloquent que viste en Eloquent y migraciones (herramienta de apoyo), sí — y eso es justo lo que necesitas para que la confirmación de solicitud de EJ6 tenga sentido de verdad.

  1. Migra el catálogo de EJ2 a un modelo Eloquent real. Crea el modelo y la migración Videojuego (titulo, genero, disponible, y también fecha_devolucion — fecha, nullable, se rellenará solo cuando el videojuego esté prestado) siguiendo el patrón guiado de Eloquent y migraciones (herramienta de apoyo), y adapta VideojuegoController para leer y escribir contra la base de datos en vez del array. Adapta también la ficha (show) para que, cuando el videojuego no esté disponible, muestre también su fecha de devolución. A partir de aquí, la disponibilidad de un videojuego es un dato persistente.
AdvertenciaErrores frecuentes

Si en EJ2 usaste @empty($videojuegos) para el catálogo vacío, revísalo ahora: empty() funciona con arrays, pero $videojuegos ya es una Collection de Eloquent, y empty() sobre un objeto siempre da false, tenga o no elementos dentro — el aviso de catálogo vacío deja de mostrarse y nadie te avisa del error. Cambia a @forelse, que trae su propio caso vacío integrado y funciona igual con arrays y con Collections.

  1. Crea app/Services/DisponibilidadService.php con, al menos, estos tres métodos (las firmas son orientativas; decide tú las estructuras de datos):

    • puedeAnadirse(int $videojuegoId, array $cesta): bool — el videojuego existe y está disponible en base de datos, no está ya en la cesta y no se supera config('prestamos.max_videojuegos').

    • fechaLimite(): string — fecha máxima de devolución: hoy + config('prestamos.dias_max') días contando solo lunes a viernes (los fines de semana no consumen días de préstamo). Este cálculo es el corazón del ejercicio: piénsalo antes de programarlo.

    • validaDevolucion(string $fecha): bool — la fecha propuesta es futura y no supera fechaLimite().

  2. Refactoriza los controladores de EJ3 y EJ4 para que toda esa lógica pase por el servicio inyectado (nada de new, y ningún cálculo de fechas ni comprobación de límites en el controlador).

  3. Justifica por escrito qué principio mejora cada extracción y qué patrón interviene en cada pieza (MVC, inyección de dependencias, responsabilidad única).

  4. Demuestra la sustituibilidad: crea DisponibilidadConFestivosService, que además descuente los festivos definidos en config('prestamos.festivos') (array de fechas), y actívala con un binding en el contenedor sin tocar ningún controlador. Documenta el antes/después de fechaLimite() con un festivo dentro del plazo.

NotaInformación

El ejercicio estará correcto si el catálogo ya vive en Eloquent (con fecha_devolucion en el esquema), la ficha muestra la fecha de devolución (cuándo toca devolverlo, no cuándo se prestó) cuando el videojuego está prestado, los tres métodos del servicio están correctos (incluido el salto de fines de semana, verificado con un caso que cruce un fin de semana), controladores sin lógica y binding alternativo demostrado.
