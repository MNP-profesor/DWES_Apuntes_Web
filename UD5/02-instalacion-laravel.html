Laravel: instalación y estructura

ImportanteNormativa · RA-CE

Este bloque trabaja CE5.b (uso de un framework de separación de capas) y CE5.e (parámetros de configuración de la aplicación).

ImportanteDocker obligatorio a partir de aquí
  • Desde esta unidad hasta el final del módulo (UD5, UD6, UD7 y UD9), todo el trabajo se hace con Docker, no es una alternativa como se permitía en UD1-UD4/UD8.
  • El motivo es que la instalación nativa de Laravel y MySQL en Windows es un foco de problemas específico de cada máquina — Docker da un entorno idéntico en cualquier equipo, evitando múltiples configuraciones distintas que depurar.

Composer: el gestor de dependencias

Composer descarga las librerías del proyecto (declaradas en composer.json) dentro de vendor/ y genera el autoloader. En otras palabras, nunca más escribirás require para cargar clases.

TipAnalogía Java

Composer es el Maven/Gradle de PHP, con una diferencia práctica: las dependencias se instalan dentro del proyecto (vendor/), no en un repositorio local compartido. Cada proyecto lleva las suyas.

Con Docker no necesitas instalar Composer en tu equipo en absoluto: usas la imagen oficial de Composer solo para el momento puntual de crear el proyecto, y a partir de ahí composer install/composer require se ejecutan dentro del contenedor.

NotaConcepto clave

composer create-project se usa una sola vez, al arrancar una aplicación nueva. A partir de ahí, para añadir funcionalidad a un proyecto que ya existe (como harás en tu proyecto intermodular, o en UD7 y UD9 de este módulo) se usa composer require sobre el proyecto ya creado, nunca se vuelve a crear el proyecto desde cero.

Crear el proyecto

Todos los ejemplos ejecutables de esta teoría se construyen sobre una agenda de contactos, deliberadamente simple para que cada concepto se vea aislado. La aplicación de préstamo de videojuegos (donde harás tú los ejercicios) es un proyecto aparte, que crearás más abajo con la misma plantilla.

docker run --rm -v "${PWD}:/app" composer create-project laravel/laravel agenda
cd agenda

Los dos ficheros que necesita todo proyecto Laravel con Docker

A diferencia de los ejercicios PHP nativos de unidades anteriores, un proyecto Laravel necesita composer install dentro del contenedor y arranca con php artisan serve, no con Apache. Estos dos ficheros, en la raíz del proyecto, son la plantilla que reutilizarás en toda la unidad (y en UD7/UD9) — para la teoría, con agenda:

Dockerfile:

FROM php:8.4-cli
# Base PHP (sin Apache, se arranca con 'php artisan serve')

RUN docker-php-ext-install pdo_mysql
# Extensión para conectar con MySQL; sin ella, "could not find driver"

COPY --from=composer:2 /usr/bin/composer /usr/bin/composer
# Copia el binario de Composer desde su imagen oficial

WORKDIR /var/www/html
# Carpeta de trabajo dentro del contenedor

docker-compose.yml:

name: ud5-teoria-agenda
# Prefijo de todos los contenedores/red/volúmenes de este proyecto.
# Evita colisiones si algún día tienes varios compose levantados a la vez.

services:
  web:
    build: .
    # Construye la imagen a partir del Dockerfile de esta misma carpeta
    # (en vez de bajar una imagen ya hecha con 'image:').

    working_dir: /var/www/html
    # Carpeta desde la que se ejecutan los comandos dentro del contenedor.

    command: php artisan serve --host=0.0.0.0 --port=8000
    # Qué ejecuta el contenedor al arrancar. --host=0.0.0.0 es obligatorio:
    # sin él, el servidor solo escucha dentro del contenedor y no sería
    # alcanzable desde el navegador de Windows.

    ports:
      - "8000:8000"
    # Puerto de tu máquina : puerto del contenedor. Así localhost:8000
    # en el navegador llega al puerto 8000 de dentro del contenedor.

    volumes:
      - ./:/var/www/html
    # Enlaza esta carpeta (tu código) con /var/www/html dentro del
    # contenedor. Los cambios que hagas en tus ficheros se reflejan
    # al instante dentro, sin reconstruir la imagen.

    environment:
      - DB_CONNECTION=mysql
      - DB_HOST=db
      - DB_DATABASE=agenda
      - DB_USERNAME=root
      - DB_PASSWORD=root
    # Variables de entorno inyectadas dentro del contenedor. Laravel las
    # lee vía getenv()/env() para configurar la conexión a base de datos
    # sin que tengas que tocar el .env a mano. DB_HOST=db funciona porque
    # 'db' es el nombre del otro servicio: dentro de la red de Docker,
    # los contenedores se resuelven entre sí por su nombre de servicio.

    depends_on:
      - db
    # Arranca 'db' antes que 'web' (orden de arranque, no espera a que
    # MySQL esté realmente listo para aceptar conexiones).

  db:
    image: mysql:8.0
    # Imagen oficial de MySQL, sin Dockerfile propio: no necesita
    # personalización, se usa tal cual.

    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: agenda
    # Estas dos variables las entiende la propia imagen de MySQL: crea
    # el usuario root con esa contraseña y una base de datos vacía
    # llamada 'agenda' automáticamente al primer arranque.

    ports:
      - "3306:3306"
    # Expone MySQL también en tu máquina (puerto estándar 3306), por si
    # quieres conectarte con un cliente externo (DBeaver, MySQL Workbench...)
    # además de desde el propio contenedor 'web'.  

    volumes:
      - agenda_db_data:/var/lib/mysql
      # Volumen NOMBRADO, no anónimo: sin esta línea, MySQL crea uno
      # anónimo por su cuenta que no siempre se reutiliza entre
      # 'docker compose down'/'up' — es fácil perder los datos sin
      # querer. Nombrarlo aquí lo hace estable y localizable con
      # 'docker volume ls'.

volumes:
  agenda_db_data:
NotaConcepto clave

Para los ejercicios de esta unidad (EJ1-EJ6), crea un segundo proyecto aparte con el mismo patrón, cambiando solo el nombre:

docker run --rm -v "${PWD}:/app" composer create-project laravel/laravel prestamos
cd prestamos

y en su docker-compose.yml: name: ud5-prestamo-videojuegos, DB_DATABASE=prestamos (en los dos sitios donde aparece: environment del servicio web y del servicio db), y en el volumen nombrado: prestamos_db_data en vez de agenda_db_data (tanto en volumes: de db como en el bloque final volumes: del fichero). No mezcles los dos proyectos — la agenda es solo para reproducir los ejemplos de teoría, nunca se entrega.

Arranca y termina la instalación dentro del contenedor:

docker compose up -d --build
# Construye la imagen y arranca web + db en segundo plano

docker compose exec web composer install
# Ejecuta 'composer install' DENTRO del contenedor 'web' ya arrancado.
# Hace falta porque el Dockerfile solo instala el binario de Composer,
# no las dependencias del proyecto: el volumen (con composer.json) no
# existe todavía durante el build, solo al arrancar el contenedor.

docker compose exec web cp .env.example .env
# Copia la plantilla de configuración a .env DENTRO del contenedor.
# Como el volumen es compartido con tu carpeta local, el .env creado
# también aparece fuera, en tu proyecto.

docker compose exec web php artisan key:generate
# Genera la clave de cifrado de la aplicación (APP_KEY) y la escribe
# en el .env. Laravel la necesita para cifrar sesiones, cookies, etc.
# Sin ella, la aplicación no arranca.

docker compose exec web php artisan migrate
# Ejecuta las migraciones: crea las tablas en la base de datos del
# servicio 'db'. Necesita que 'db' ya esté arrancado y aceptando
# conexiones (por eso depends_on en el compose, aunque no garantiza
# que MySQL esté "listo", solo que el contenedor está iniciado).

Abre http://localhost:8000: verás la página de bienvenida de Laravel. Ya tienes una aplicación MVC funcionando.

AdvertenciaErrores frecuentes

Si al arrancar ves could not find driver al usar la base de datos, revisa que el Dockerfile tiene la línea RUN docker-php-ext-install pdo_mysql y que reconstruiste la imagen con --build después de añadirla — la imagen base php:8.4-cli no la trae de serie.

La estructura de carpetas

Directorio Qué contiene Lo usarás para…
app/ Tu código: app/Models y app/Http/Controllers Modelos y controladores
routes/ Definición de rutas routes/web.php en toda la unidad
resources/views/ Las vistas Blade (.blade.php) Todas tus pantallas
config/ Configuración legible con config() Bloque de configuración
public/ Único directorio visible desde el navegador CSS, JS, imágenes
storage/ Ficheros generados: logs, caché, sesiones Consultar storage/logs/laravel.log
database/ Migraciones, seeders, factorías Herramienta de apoyo: la usarás en la sección de Eloquent, no se estudia en profundidad aquí
.env Variables de esta instalación concreta No se sube al repositorio
NotaConcepto clave

Front controller: toda petición entra por public/index.php, que arranca el framework y delega en el enrutador. Es lo contrario de UD2–UD4, donde cada página era un .php accesible directamente. Por eso solo public/ está expuesto: el resto del código queda fuera del alcance del navegador.

artisan: la consola de Laravel

artisan genera código, inspecciona la aplicación y arranca servicios. Con Docker, cada comando se ejecuta anteponiendo docker compose exec web:

docker compose exec web php artisan list            
# Todos los comandos disponibles

docker compose exec web php artisan route:list      
# Esquema del enrutado

docker compose exec web php artisan make:controller NombreController  
# No lo ejecutes aún, se utilizará en la sección rutas y controladores

docker compose exec web php artisan make:model Nombre                 
# No lo ejecutes aún, se utilizará en la sección Eloquent y migraciones

Ejemplo real de route:list en un proyecto recién creado:

docker compose exec web php artisan route:list
  GET|HEAD   / ...................................................
  GET|HEAD   storage/{path} .......................... storage.local
  PUT        storage/{path} ................... storage.local.upload
  GET|HEAD   up ...................................................

                                                     Showing [4] routes

Cada fila: método HTTP, URI, nombre de la ruta y acción que la atiende.

.env y la configuración

.env guarda lo que cambia entre máquinas (tu portátil, el servidor del centro, producción): credenciales, URLs, modo de depuración. Los ficheros de config/ leen esos valores con env() y el código de la aplicación los consume siempre con config():

Modifica el nombre de la app:

# .env
APP_NAME="Agenda DAW"

Luego, en routes/web.php:

Route::get('/nombre', fn () => config('app.name'));

Visitando http://localhost:8000/nombre:

Agenda DAW

La cadena completa es: .env → config/app.php (que hace 'name' => env('APP_NAME', 'Laravel')) → config('app.name') en tu código.

AdvertenciaErrores frecuentes
  • Llamar a env('APP_NAME') desde un controlador o una vista. Esto funciona hasta que en producción se cachea la configuración (php artisan config:cache) y env() empieza a devolver null fuera de config/. Regla: env() solo dentro de config/; en tu código, siempre config().
  • Editar .env y no ver el cambio: reinicia el contenedor (docker compose restart web) y, si cacheaste, docker compose exec web php artisan config:clear.
  • Subir .env al repositorio. Contiene credenciales; por eso Laravel lo incluye en .gitignore.
  • Poner las credenciales de base de datos directamente en .env en vez de en el docker-compose.yml (environment:) cuando trabajas con Docker: si algún día compartes el proyecto, es fácil olvidar que .env también tiene que coincidir con lo que definiste en el compose.
