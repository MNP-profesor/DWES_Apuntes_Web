Cookies persistentes y control de acceso por roles

ImportanteNormativa · RA-CE
  • CE4.c. — Se han utilizado mecanismos para almacenar información en el cliente web y para recuperar su contenido.
  • CE4.e. — Se han escrito aplicaciones que integren mecanismos de autentificación de usuarios.

Casilla «recordarme»

Con token fijo

La cookie de sesión (PHPSESSID) desaparece normalmente al cerrar el navegador. Si quieres que el usuario siga dentro al volver al día siguiente hace falta algo más duradero: la casilla «Recordarme».

El flujo mínimo cuando se hace Login con la casilla «Recordarme» marcada es:

  1. El servidor genera un token (una cadena aleatoria larga).
  2. Lo guarda asociado al usuario (aquí, en un fichero).
  3. Lo envía al navegador en una cookie recordarme con los flags de seguridad correspondientes. Duarará varios dias, según la expiración asignada.
  4. Cuando el usuario vuelve sin sesión pero sí hay cookie recordarme, el servidor lee esa cookie y se busca el token.
  5. Si existe token, se inicia la sesión (con session_regenerate_id(true)); sin pedir la contraseña. Si no existe token, se borra la cookie.
  6. Cuando se hace Logout, se borra el token del servidor y la cookie, además de cerrar la sesión.

¿Por qué se utiliza un token y no el email o la contraseña dentro de la cookie? Porque el usuario puede leer y modificar sus cookies: con solo el email cualquiera se haría pasar por otro, y la contraseña nunca debe viajar así. El token no se puede adivinar y se puede borrar del servidor cuando haga falta (por ejemplo, al cerrar sesión) sin tocar la contraseña.

Con rotación de token

El flujo anterior (un token fijo guardado en cookie) tiene un problema: si alguien roba esa cookie, tiene acceso indefinido.

Una versión más robusta rota el token en cada uso: cada vez que se usa para reconectar, se genera uno nuevo y se invalida el anterior. Así, si el usuario legítimo y un atacante tienen copias del mismo token y uno de los dos lo usa, el otro deja de servir. Esto sería una señal detectable de robo.

Con rotación, del paso 4 en adelante el flujo cambia: se busca el token y se consume (se invalida en ese mismo momento). Si era válido, se inicia la sesión, se genera un token nuevo, se guarda y se envía la cookie con el valor nuevo. Si no era válido (no existe o ya se gastó), se borra la cookie y se redirige al login.

// Importante: "consumir" un token debe invalidarlo antes de devolver el email
// (&$tokensValidos: el array se pasa por referencia, para que el unset() afecte al original)

function consumirToken(array &$tokensValidos, string $token): ?string {
    if (!isset($tokensValidos[$token])) {
        return null; // token inválido o ya usado: posible robo
    }
    $email = $tokensValidos[$token];
    unset($tokensValidos[$token]); // se invalida: de un solo uso
    return $email;
}

Veámoslo con un ejemplo. El usuario tiene la cookie con el token T1:

Paso Qué ocurre Resultado
1 El usuario vuelve sin sesión: consumirToken(T1) Devuelve su email; T1 queda invalidado y se emite T2
2 Un atacante que había copiado T1 lo usa: consumirToken(T1) Devuelve null: rechazado
3 El usuario vuelve otra vez con T2: consumirToken(T2) Devuelve su email; se emite T3

Si el atacante hubiera usado T1 antes que el usuario, ocurriría al revés: el rechazado sería el usuario legítimo, que tendría que volver a iniciar sesión con su contraseña. Esa es la señal de robo.

NotaConcepto clave

El token de “recordarme” nunca es la contraseña ni un hash de ella: es un valor aleatorio independiente (random_bytes(), nunca rand()) que se puede invalidar en cualquier momento sin afectar a la contraseña real. En un sistema real, además, se guarda un hash del token (no el token en claro) y su fecha de caducidad. El ejercicio de esta sección te pide construir el repositorio completo (guardarlo en fichero, no en un array de memoria como el ejemplo de arriba) y la rotación: emitir un token nuevo cada vez que uno se consume con éxito.

Control de acceso por roles, con varios niveles

Hasta ahora hemos resuelto la autenticación comprobando quién es el usuario (el login). Falta la autorización: decidir qué puede hacer cada usuario ya identificado. No todo el mundo debe poder, por ejemplo, editar contenido o ver informes. La forma habitual es asignar a cada usuario un rol (usuario, editor, administrador…) y definir qué permisos (acciones concretas) tiene cada rol.

Hay dos respuestas distintas cuando se deniega el acceso:

  1. Si no hay sesión (no está autenticado), se redirige al login.

  2. Si hay sesión pero no permiso (está autenticado, pero no autorizado), se responde con un 403 («Acceso denegado»).

En una aplicación real el rol se guarda junto al usuario (en el fichero o la base de datos) y se carga en la sesión al hacer login. En esta unidad, para centrarnos en los permisos, los roles se implementan como clases y se instancian a mano.

Con más de dos roles conviene un mapa explícito de permisos por rol en lugar de ir acumulando array_merge() en cada subclase, que se vuelve difícil de leer a partir de tres niveles.

AdvertenciaErrores frecuentes

La clase de este apartado se llama UsuarioRol, no Usuario. En la sección de login/registro ya se define su propia clase Usuario (email + contraseña), completamente distinta de esta.

abstract class UsuarioRol {
    protected string $email;

    public function __construct(string $email) {
        $this->email = $email;
    }

    abstract public function rol(): string;

    public function permisos(): array {
        $mapaPermisos = [
            'usuario' => ['ver_perfil'],
            'editor'  => ['ver_perfil', 'editar_contenido'],
            // Un tercer rol se añadiría aquí, con su propia lista de permisos
        ];

        /*
        Con un rol desconocido que no está en el mapa, PHP lanzaría un aviso de clave indefinida y devolvería null, pero como la función declara que devuelve un array, PHP devolvería un TypeError.
        */
        return $mapaPermisos[$this->rol()] ?? []; // <-- MUY IMPORTANTE añadir valor por defecto
    }

    public function tienePermiso(string $permiso): bool {
        return in_array($permiso, $this->permisos(), true);
    }
}

class UsuarioNormal extends UsuarioRol {
    public function rol(): string { return 'usuario'; }
}

class Editor extends UsuarioRol {
    public function rol(): string { return 'editor'; }
}
function requierePermiso(UsuarioRol $usuario, string $permiso): void {
    if (!$usuario->tienePermiso($permiso)) {
        http_response_code(403);
        exit('Acceso denegado');
    }
}

$actual = new Editor('manel@edu.gva.es');
requierePermiso($actual, 'editar_contenido');    // pasa
requierePermiso($actual, 'gestionar_usuarios');  // 403 Acceso denegado (permiso ni siquiera existe en el mapa)
AdvertenciaErrores frecuentes

Comprobar el rol con if ($usuario->rol() === 'administrador') en cada página protegida se vuelve inmanejable en cuanto hay varias combinaciones de permisos por rol (por ejemplo, “editor o administrador pueden hacer X”). Centraliza los permisos en un único mapa, como arriba, y comprueba siempre el permiso, no el rol, en cada página. El ejercicio de esta sección añade un tercer rol (Administrador) y tres páginas protegidas distintas.

Actividades

EJ13 · «Recordarme» con rotación de token

Implementa el flujo completo de “recordarme” con rotación de token, persistiendo los tokens en un fichero (por ejemplo JSON, como el UsuarioRepository de la sección anterior) en vez del array en memoria usado como ilustración en la teoría: crear token al marcar la casilla, consumirlo (invalidándolo) al reconectar automáticamente, y emitir uno nuevo tras cada uso. Aplica también los flags de seguridad de la cookie vistos en la sección de cookies. Comprueba que, si intentas reutilizar un token ya consumido (simula guardarte una copia de la cookie antes de que se rote y vuelve a usarla), el sistema lo rechaza y borra la cookie.

TipCómo comprobar la rotación

  1. Inicia sesión marcando «Recordarme»: en F12 → Application → Cookies aparece recordarme, con HttpOnly y SameSite. Copia su valor (token T1).

  2. Borra la cookie PHPSESSID y recarga el panel: entras sin login y el valor de recordarme ha cambiado (token T2).

  3. Pega T1 de nuevo en la cookie y recarga: te rechaza y borra la cookie.

  4. En un script aparte, comprueba lo mismo sin navegador:

consumir(T1) -> 'ana@example.com'   (y emite T2)
consumir(T1) -> null                (ya gastado)
consumir(T2) -> 'ana@example.com'   (sigue valiendo)

EJ14 · Tres roles con mapa de permisos

Parte de las clases UsuarioRol, UsuarioNormal y Editor y de la función requierePermiso() que ya tienes en el código de arriba, y amplíalas:

  1. Crea la clase Administrador (extendiendo UsuarioRol) y añade su entrada al mapa de permisos de UsuarioRol. Un administrador debe poder hacer todo lo que hace un editor, y además gestionar_usuarios y ver_informes. Escribe los permisos en el mapa, sin usar array_merge() con parent:: en la subclase.

  2. Crea tres páginas protegidas, cada una exigiendo un permiso distinto con requierePermiso():

    • editar.php → editar_contenido
    • admin.php → gestionar_usuarios
    • informes.php → ver_informes

Para probarlas sin depender todavía del login real, instancia el usuario a mano al principio de cada página (por ejemplo, $actual = new Editor('manel@edu.gva.es');) y cambia la clase para comprobar cada caso.
