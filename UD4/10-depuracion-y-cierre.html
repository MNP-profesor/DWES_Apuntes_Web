Depuración y cierre de la unidad

ImportanteNormativa · RA-CE

CE4.f. — Se han utilizado herramientas y entornos para facilitar la programación, prueba y depuración del código.

Herramientas de depuración

Depurar aplicaciones con estado (sesiones, cookies) tiene una particularidad: el error no siempre es visible en la petición actual, sino en la siguiente.

session_start();
var_dump($_SESSION); // inspección rápida de todo lo que hay guardado
print_r($_COOKIE); // igual, pero para cookies

  • var_dump()/print_r() son rápidas y no requieren instalar nada, pero tienen un límite: solo muestran lo que tú decidas imprimir, en el punto exacto donde pongas la línea.

  • Cuando el fallo no es evidente a simple vista, Xdebug permite parar la ejecución en cualquier línea e inspeccionar todas las variables en ese momento, sin tener que ir añadiendo var_dump() uno a uno.

Configurar Xdebug (una sola vez por proyecto)

Instalación (igual en los dos casos, cambia solo cómo la activas después):

  • Con Docker, en tu Dockerfile:
RUN pecl install xdebug && docker-php-ext-enable xdebug
  • Con XAMPP, descarga la DLL de Xdebug correspondiente a tu versión de PHP desde xdebug.org/wizard y colócala en la carpeta ext/ de tu instalación de PHP.

Configuración:

  • Con Docker, en tu docker-compose.yml, junto al resto de variables del servicio web:
services:
  web:
    build: .
    environment:
      - XDEBUG_MODE=debug
      - XDEBUG_CONFIG=client_host=host.docker.internal
      # ...el resto de variables que ya tengas (DB_HOST, etc.)
  • Con XAMPP, en tu php.ini (accesible desde el panel de control de XAMPP → “Config” → PHP (php.ini)):
zend_extension=xdebug
xdebug.mode=debug
xdebug.start_with_request=yes
xdebug.client_host=localhost

Después de editar php.ini, reinicia Apache desde el panel de XAMPP para que el cambio surta efecto.

Editor (igual en los dos casos):

  1. Instala la extensión “PHP Debug” en VS Code (marketplace de extensiones).
  2. Ctrl+Shift+D → “crear archivo launch.json” → elige “PHP” — VS Code genera la configuración por defecto, que suele funcionar sin tocar nada más.

Usarlo (cada vez que depures)

  1. Clic a la izquierda del número de línea donde quieras parar (aparece un punto rojo).
  2. F5 para arrancar la depuración, y después haz la petición desde el navegador — el editor se para en tu punto de ruptura, mostrando el valor de cada variable en el panel lateral.
TipPractica con el ejemplo de al lado

Antes de EJ15, prueba Xdebug sobre el login.php con los 3 fallos que tienes justo debajo: pon un punto de ruptura en la línea del if ($usuario->verificarPassword(...)) y observa qué vale $usuario cuando el email no existe — verás en directo por qué revienta, sin necesidad de que te lo cuente el texto.

Un caso con varios fallos a la vez

En una aplicación real, los bugs rara vez vienen solos. Este fragmento de una página de login tiene tres fallos distintos — la depuración eficaz consiste en aislarlos uno a uno, no en cambiar cosas al azar hasta que “parezca” que funciona.

Antes del fragmento, esto es lo que necesitas para poder ejecutarlo (no forma parte de los fallos a buscar, es solo el andamiaje):

<?php
require_once __DIR__ . '/Usuario.php';
require_once __DIR__ . '/UsuarioRepository.php';

$repositorio = new UsuarioRepository(__DIR__ . '/datos/usuarios.json');

Y ahora sí, el fragmento con los tres fallos:

// login.php — versión con errores
echo "<h1>Iniciar sesión</h1>"; // (1)

session_start();

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $usuario = $repositorio->buscarPorEmail($_POST['email']);

    if ($usuario->verificarPassword($_POST['password'])) { // (2)
        $_SESSION['usuario_id'] = $usuario->getEmail();
        header('Location: /panel.php'); // (3)
        echo 'Redirigiendo...';
    } else {
        echo 'Credenciales incorrectas';
    }
}

Proceso de diagnóstico, paso a paso:

  1. Síntoma: nada más cargar la página, PHP muestra un aviso “headers already sent” y la sesión no se guarda. Causa: el echo "<h1>..." en la línea (1) envía salida antes de session_start(). Corrección: mover session_start() a la primera línea del script.
  2. Síntoma: con un email que no existe, la página da un error fatal en vez de mostrar “Credenciales incorrectas”. Causa: en la línea (2), si buscarPorEmail() devuelve null, llamar a $usuario->verificarPassword() sobre null revienta el script. Corrección: comprobar $usuario !== null antes de usarlo, exactamente como en la de login y registro.
  3. Síntoma: tras un login correcto, el navegador no redirige, y además puede aparecer un error “headers already sent” en la línea del header(). Causa: falta exit; después del header() en la línea (3), y además el echo 'Redirigiendo...' intenta escribir salida después de haber llamado a header(). Corrección: añadir exit; justo después del header() y quitar ese echo.
// login.php — corregido
session_start(); // (1) corregido: primera línea, sin salida antes

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $usuario = $repositorio->buscarPorEmail($_POST['email']);

    if ($usuario !== null && $usuario->verificarPassword($_POST['password'])) { // (2) corregido
        $_SESSION['usuario_id'] = $usuario->getEmail();
        header('Location: /panel.php');
        exit; // (3) corregido
    } else {
        echo 'Credenciales incorrectas';
    }
}
AdvertenciaErrores frecuentes

Cuando encuentres un bug, resiste la tentación de arreglar el primer síntoma y dar por cerrado el caso. Vuelve a probar el flujo completo (usuario correcto, usuario inexistente, contraseña incorrecta) después de cada corrección: es habitual que un mismo script tenga más de un fallo independiente, como en el ejemplo anterior.

Actividades

EJ15 · Depuración de una aplicación con varios fallos

Se te entrega el siguiente fragmento de una página de “recordarme” con dos fallos independientes. Localízalos con var_dump()/Xdebug (no te limites a leer el código: ejecútalo y observa el comportamiento real) y documenta, para cada uno, el síntoma que provocó, la causa y la corrección — igual que en la tabla de diagnóstico de esta sección.

Antes del fragmento con los fallos, necesitas estas piezas mínimas para poder ejecutarlo (no forman parte de los fallos a buscar, son solo el andamiaje para que el script funcione):

<?php
// Simulación mínima de apoyo — no contiene ninguno de los dos fallos
class UsuarioSimulado {
    public function getEmail(): string { return 'ana@example.com'; }
}
$usuario = new UsuarioSimulado();

function guardarTokenParaUsuario(string $email, string $token): void {
    $datos = file_exists('tokens.json') ? json_decode(file_get_contents('tokens.json'), true) : [];
    $datos[$token] = $email;
    file_put_contents('tokens.json', json_encode($datos));
}

function buscarUsuarioPorToken(?string $token): ?string {
    if ($token === null || !file_exists('tokens.json')) {
        return null;
    }
    $datos = json_decode(file_get_contents('tokens.json'), true);
    return $datos[$token] ?? null;
}

Y ahora sí, el fragmento con los dos fallos a localizar:

session_start();

if (isset($_POST['recordarme'])) {
    $token = bin2hex(random_bytes(32));
    setcookie('recordarme', $token, time() + 86400 * 30);
    guardarTokenParaUsuario($usuario->getEmail(), $token);
}

if (!isset($_SESSION['usuario_id'])) {
    $email = buscarUsuarioPorToken($_COOKIE['recordarme']);
    $_SESSION['usuario_id'] = $email;
}

var_dump($_SESSION['usuario_id'] ?? 'no hay sesión');
var_dump(isset($_COOKIE['recordarme']) ? 'cookie presente' : 'cookie ausente');

Proyecto integrador

EJ16 · Mini-aplicación con registro, login y panel protegido

Construye una pequeña aplicación que combine, en un único flujo coherente, todo lo trabajado en esta unidad. Puedes —y debes— reutilizar el código de ejercicios anteriores en vez de escribirlo desde cero: lo que se evalúa aquí es que todas las piezas encajen entre sí, no que cada pieza sea nueva.

Debe incluir:

  1. Registro: formulario que crea un usuario con la contraseña cifrada mediante password_hash(), validando el formato del email y que no exista ya.
  2. Login: valida credenciales con password_verify() e inicia sesión regenerando el ID.
  3. Una preferencia en cookie: al menos un dato de usuario (idioma o tema) guardado en cookie, con los flags de seguridad vistos en la unidad.
  4. Panel protegido: una página solo accesible con sesión activa, que redirige a login si no la hay.

Cierre de la unidad

Con esto tienes todo lo necesario para construir una aplicación web con estado: clases bien diseñadas, sesiones para el estado activo, cookies para lo persistente, contraseñas cifradas correctamente y control de acceso por roles. Es exactamente la base sobre la que trabajarás en la siguiente unidad, donde este mismo código se reorganiza usando un framework (Laravel) en lugar de escribirlo a mano.
